# VakeTomate Power BI Automation

## Status

Design specification derived from the first manual implementation of the **Tutkimusrahoituksen vuosikalenteri** in Power BI.

This document defines how Power BI automation should become a first-class VakeTomate module/app. The manual report being built now is the reference implementation: every useful manual transformation, relationship, DAX pattern, visual interaction and publishing rule should become a reproducible automation step where feasible.

---

## 1. Purpose

The Power BI Automation module will turn approved organisational source data (initially Excel / Excel Online) into a validated, Power BI-ready reporting model and, where organisational Microsoft/Fabric permissions allow, create or update the report itself.

The first supported use case is a research-funding annual calendar (Tutkimusrahoituksen vuosikalenteri), but the architecture must be reusable for other VakeTomate reporting workflows, including the future koulutusvuosikello and other operational dashboards.

The user should not need to repeat low-level Power Query, relationship, DAX, filtering and visual-configuration work for every workbook/report.

## 2. Reference user experience

### 2.1 Input

User selects or connects an approved Excel/Excel Online source.

Initial reference schema:

- Kuukausi_nro
- Kuukausi
- Kvartaali
- Kvartaali_alkaa
- Kvartaali_päättyy
- Rahoittaja
- Kategoria
- Hakija_Postdoc
- Hakija_Professori
- Hakija_Tutkimusprojekti
- Ala_Kaikki
- Ala_Lääketiede
- Ala_Terveys
- Ala_Sosiaali
- Ala_Tekniikka
- Ala_Pelastustoimi
- Ala_Talous
- Jatkuva_haku
- Kuvaus
- Linkki
- Huomiot

Recommended additions for duration-aware calendars:

- Haku_ID (stable source ID; generated by VakeTomate when missing)
- Haku_nimi (short user-facing call title)
- Haku_alkaa (actual call opening date)
- Haku_päättyy (actual call closing date)

### 2.2 Validation screen

Before generating Power BI artefacts, VakeTomate should display validation results such as:

- required columns found / missing
- row count
- duplicate records / duplicate IDs
- invalid or missing dates
- month/quarter inconsistencies
- unknown Kyllä/Ei values
- missing URLs
- malformed URLs
- unknown categories
- blank required fields
- stale/unreviewed records where review metadata exists

No transformation should silently discard questionable records. Warnings must be explicit and traceable.

### 2.3 One-action preparation

Primary action: **Valmistele Power BI:lle**.

The module then produces the normalized model and, in advanced deployments, updates the Power BI/Fabric artefacts automatically.

## 3. Data normalization rules

### 3.1 Kyllä/Ei normalization

Normalize Yes/No source columns by:

1. trimming whitespace
2. removing non-printing characters
3. normalizing case
4. mapping allowed values to canonical `KYLLÄ` / `EI`
5. flagging unknown values rather than guessing

Reference columns include applicant, discipline and continuous-call flags.

### 3.2 Stable technical ID

If `Haku_ID` is missing, generate a technical ID.

For production automation, prefer a stable deterministic ID over a row index whenever possible, so updates do not change identity merely because row order changed.

Possible strategy:

`hash(normalized funder + normalized call name + opening date + source URL)`

A generated ID must be stored in the prepared output and reused on subsequent refreshes.

### 3.3 Applicant bridge

Convert wide Yes/No columns such as:

- Hakija_Postdoc
- Hakija_Professori
- Hakija_Tutkimusprojekti

into a normalized bridge table:

`Bridge_Hakijat(Haku_ID, Hakijatyyppi)`

Only canonical `KYLLÄ` values become rows.

Example:

| Haku_ID | Hakijatyyppi |
|---|---|
| 17 | Postdoc |
| 17 | Tutkimusprojekti |

### 3.4 Discipline/service bridge

Convert wide fields such as:

- Ala_Kaikki
- Ala_Lääketiede
- Ala_Terveys
- Ala_Sosiaali
- Ala_Tekniikka
- Ala_Pelastustoimi
- Ala_Talous

into:

`Bridge_Alat(Haku_ID, Ala)`

The handling of `Ala_Kaikki` must be configurable. If organisational semantics confirm that it means every defined discipline, the automation should expand it to all valid disciplines for filtering while retaining the original source value for auditability.

### 3.5 Duration-aware month bridge

When exact `Haku_alkaa` and `Haku_päättyy` dates are available, generate:

`Bridge_HakuKuukaudet(Haku_ID, Vuosi, Kuukausi_nro, Kuukausi, Kvartaali)`

A call spanning June–September must be present in June, July, August and September filtering contexts, not only its start month.

Continuous calls should use explicit open-ended semantics; any artificial year-end date used for visualization must be clearly marked as a display boundary, not a real closing date.

## 4. Power BI semantic model

Initial reference model:

```text
Bridge_Hakijat (*) ---- (1) Fact_Rahoitushaut (1) ---- (*) Bridge_Alat
                                  |
                                  | 1
                                  |
                                  *
                         Bridge_HakuKuukaudet
```

### 4.1 Relationships

Reference implementation currently requires bridge slicers to filter the fact table. The generated model must intentionally configure relationship/filter behavior and test it rather than relying on Power BI auto-detection.

The automation should validate:

- `Fact_Rahoitushaut[Haku_ID]` is unique
- bridge IDs exist in the fact table
- no orphan rows
- intended relationships are active
- filter propagation matches report behavior

As the model grows, VakeTomate should prefer a clean star-schema design and avoid uncontrolled bidirectional relationship chains.

## 5. DAX generated by the module

The current reference report uses selected-record measures so a user can click one funding call and see its details.

Examples:

```DAX
Valittu_Kuvaus =
IF(
    HASONEVALUE(Fact_Rahoitushaut[Haku_ID]),
    SELECTEDVALUE(Fact_Rahoitushaut[Kuvaus]),
    "Valitse rahoitushaku alla olevasta kalenterista"
)
```

```DAX
Valittu_Rahoittaja =
IF(
    HASONEVALUE(Fact_Rahoitushaut[Haku_ID]),
    SELECTEDVALUE(Fact_Rahoitushaut[Rahoittaja]),
    BLANK()
)
```

```DAX
Valittu_Kategoria =
IF(
    HASONEVALUE(Fact_Rahoitushaut[Haku_ID]),
    SELECTEDVALUE(Fact_Rahoitushaut[Kategoria]),
    BLANK()
)
```

```DAX
Valittu_Huomiot =
IF(
    HASONEVALUE(Fact_Rahoitushaut[Haku_ID]),
    SELECTEDVALUE(Fact_Rahoitushaut[Huomiot]),
    BLANK()
)
```

```DAX
Valittu_Linkki =
IF(
    HASONEVALUE(Fact_Rahoitushaut[Haku_ID]),
    SELECTEDVALUE(Fact_Rahoitushaut[Linkki]),
    BLANK()
)
```

```DAX
Valittu_Hakijat =
IF(
    HASONEVALUE(Fact_Rahoitushaut[Haku_ID]),
    CONCATENATEX(
        VALUES(Bridge_Hakijat[Hakijatyyppi]),
        Bridge_Hakijat[Hakijatyyppi],
        ", "
    ),
    BLANK()
)
```

```DAX
Valitut_Alat =
IF(
    HASONEVALUE(Fact_Rahoitushaut[Haku_ID]),
    CONCATENATEX(
        VALUES(Bridge_Alat[Ala]),
        Bridge_Alat[Ala],
        ", "
    ),
    BLANK()
)
```

The generator must respect the target model locale/DAX argument separator when required.

## 6. Report UX specification

### 6.1 No-scroll design principle

Primary report pages should fit into one standard desktop viewport (target 16:9) without requiring page-level scrolling.

If data volume exceeds what can be legibly shown at once, use filtering, hierarchy, drillthrough or separate views instead of microscopic text.

### 6.2 Top filter controls

The main calendar page should provide user-selectable controls for:

- Kvartaali (Q1/Q2/Q3/Q4)
- Kuukausi
- Hakijatyyppi
- Ala
- Kategoria
- Jatkuva haku
- optional Rahoittaja

Important distinction:

- **Slicers/dropdowns are filters chosen by the user.**
- **Selected-record cards/text are outputs showing the call the user clicked.**

Therefore `Rahoittaja`, `Kategoria`, `Hakija`, and `Ala` may appear both as optional top filters and as selected-call detail fields. They serve different purposes and should not be conflated.

Recommended compact implementation:

- Q1–Q4: button/tile slicer
- months: horizontal button/tile slicer when space permits
- applicant / discipline / category / funder: dropdown slicers for compact layout
- Jatkuva haku: compact two-state control or user-friendly boolean filter

### 6.3 Selected funding-call detail panel

When exactly one call is selected from the calendar/Gantt, show:

- Rahoittaja
- Kategoria
- Hakija(t)
- Ala(t)
- Kuvaus
- Huomiot
- Jatkuva haku
- link/open action

Long fields such as `Kuvaus` and `Huomiot` should use dynamic text capable of wrapping without horizontal scrolling.

Short fields may use cards.

When no single call is selected, show a clear instruction such as:

`Valitse rahoitushaku alla olevasta kalenterista`.

### 6.4 Annual calendar / Gantt

The production calendar should not expose mysterious record-count numbers.

Preferred behavior:

- row = funding call (prefer `Haku_nimi`)
- grouping/resource = Rahoittaja where useful
- horizontal time axis = calendar months/dates
- bar = actual `Haku_alkaa` → `Haku_päättyy`
- continuous calls = visually distinct/open-ended indicator
- click a bar = select exactly one `Haku_ID` and update the detail panel

The prototype count matrix is a validation visual only and should be removed once the Gantt/calendar replacement is proven.

### 6.5 Interaction rules

Desired interaction flow:

```text
Top slicers
    ↓
filter annual calendar/Gantt
    ↓
user clicks one funding call
    ↓
selected-call detail panel updates
```

Selecting a funding call should not unnecessarily collapse or mutate the top slicer choices. Report interaction settings should be generated/tested accordingly.

## 7. Report automation levels

### Level 1 — Data preparation

VakeTomate:

- ingests workbook
- validates schema/content
- normalizes data
- creates bridge/dimension outputs
- emits Power BI-ready files/tables
- emits generated DAX/relationship specification

No Power BI write permission is required.

### Level 2 — Model automation

Where Microsoft/Fabric APIs and tenant permissions allow:

- create/update semantic model assets
- create relationships
- create measures
- apply data types/sort-by columns
- configure refresh connection

### Level 3 — Report automation

Where supported/approved:

- create/update report definition
- create pages
- create slicers
- create detail panel
- create Gantt/calendar visual or approved fallback
- configure visual interactions
- apply theme/branding
- bind report to semantic model

### Level 4 — Operational automation

- trigger/monitor refreshes
- detect source changes
- validate report after refresh
- surface warnings before publication
- maintain last-checked / data-quality status
- optionally support approval workflow before publishing refreshed content

## 8. Security and governance

This module handles organisational data and must be designed for enterprise controls from the beginning.

Requirements:

- do not require users to copy confidential workbooks to personal devices/services
- preserve tenant boundaries
- least-privilege Microsoft Graph/Fabric/Power BI permissions
- use organisation-approved storage/connectors
- never use public `Publish to web` for internal reports
- log transformations and generated artefacts
- retain source lineage
- no silent data deletion
- configurable retention of temporary processing files
- auditable refresh/update history
- tenant/workspace authorization checks
- support restricted custom-visual policies

Where a custom Gantt visual is not permitted, VakeTomate must generate an approved native visual fallback rather than bypass tenant policy.

## 9. Architecture direction

Suggested module boundary:

```text
VakeTomate
└── Power BI Automation
    ├── Source Connector
    │   ├── Excel upload
    │   └── Excel Online / SharePoint (future connector)
    ├── Schema Detector
    ├── Validator
    ├── Normalizer
    ├── Model Generator
    │   ├── fact table
    │   ├── bridge/dimension tables
    │   ├── relationships
    │   └── DAX measures
    ├── Report Generator
    │   ├── filters/slicers
    │   ├── selected-record panel
    │   ├── annual calendar/Gantt
    │   ├── interactions
    │   └── theme
    ├── Fabric/Power BI Adapter
    ├── Refresh/Publishing Orchestrator
    └── Validation & Audit Report
```

Implementation should separate generic Power BI/report-generation primitives from the research-funding-specific configuration so future report types can reuse the engine.

## 10. Configuration-driven report templates

Avoid hard-coding the research-funding report into the automation engine.

A report template/config should define:

- source schema aliases
- required and optional fields
- normalization mappings
- bridge transformations
- relationships
- generated measures
- slicers
- detail fields
- timeline start/end fields
- category color mappings
- visual layout
- accessibility labels
- security/publication policy

This allows later templates such as:

- Tutkimusrahoituksen vuosikalenteri
- Koulutusvuosikello
- funding monitoring dashboard
- project portfolio calendar
- other VakeTomate operational reports

Complete and document the current Power BI annual-calendar report, including all successful transformations, DAX, interactions, layout choices and user feedback.

- `Fact_Rahoitushaut`

- `Bridge_Alat`

### Milestone D — Microsoft/Fabric integration

Add authenticated tenant-aware creation/update/refresh operations subject to approved permissions.

### Milestone E — VakeTomate UI

Provide a dedicated VakeTomate app/module with:

1. select/connect source
2. map/validate fields
3. preview issues
4. choose report template
5. generate/update report
6. inspect validation results
7. publish/refresh only when authorised

## 12. Acceptance criteria for the research-funding template

The generated report is acceptable when:

- no page-level scrolling is needed at the target viewport
- quarter/month/applicant/discipline/category/continuous-call filters work
- optional funder filter can be enabled
- filters combine correctly
- one selected call drives the detail panel
- description and notes wrap/read without horizontal scrolling
- source URL opens the selected call
- annual duration is visually understandable without count numbers
- continuous calls are clearly distinguished
- calls spanning multiple months are filterable from every month they occupy
- confidential data remains within approved organisational systems
- the generated model passes validation with no orphan IDs or invalid relationships
- source updates can refresh without rebuilding the report manually
